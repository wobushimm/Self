# DNS 中继器验收准备

> 本文严格按当前 `dns_relay.py` 和 `dnsrelay.txt` 的实际实现编写。不要把“可以继续完善”的功能说成已经实现。

## 一、30 秒项目介绍

我们实现了一个基于 Python 和 UDP Socket 的 DNS 中继器。程序监听客户端的 DNS 查询，先查本地配置表：IPv4 映射构造 A 响应，IPv6 映射构造 AAAA 响应；配置为 `0.0.0.0` 的域名对所有查询类型返回 NXDOMAIN；本地没有匹配时，为请求分配新的 DNS Transaction ID 并转发到上游，收到响应后恢复客户端原来的 ID。程序还实现了 DNS 域名解析、压缩指针解析、异常报文检查、并发请求映射、超时清理和日志输出。

一句话概括：**本地能回答的自己回答，不能回答的交给上游，并确保上游响应回到正确客户端。**

## 二、展示流程（建议 4～6 分钟）

Wireshark 抓包属于独立的验证与展示环节，不需要修改 DNS Relay 的代码。Windows 下的完整操作、过滤器、截图字段和 Testing and results 表格见 [`Wireshark抓包与测试结果.md`](./Wireshark抓包与测试结果.md)。需要一次发出本地解析、黑名单和上游转发三组查询时，可在 Wireshark 开始抓包后运行 [`run_wireshark_demo.ps1`](./run_wireshark_demo.ps1)。

### 1. 展示文件（20 秒）

- `dns_relay.py`：中继器主程序。
- `dnsrelay.txt`：本地域名表，格式为 `IP 域名`。
- 当前有三条地址规则，涉及两个域名：
  - `www.bupt.com.cn -> 114.255.40.66`：本地直接解析。
  - `www.bupt.com.cn -> 2001:db8::66`：本地返回示例 IPv6 地址。
  - `www.666.com -> 0.0.0.0`：A、AAAA 等查询均返回 NXDOMAIN。

### 2. 启动程序（30 秒）

程序兼容课程 PPT 第 34 页的启动格式：

```text
dnsrelay [-d|-dd] [dns-server-ipaddr] [filename]
```

Windows 下可直接使用随项目提供的批处理入口：

```powershell
dnsrelay -dd 114.114.114.114 dnsrelay.txt
```

其中 `-d` 输出调试摘要，`-dd` 还会输出 DNS 报文字节，便于与 Wireshark 对照。不传上游地址和文件名时，默认使用 `114.114.114.114` 和 `dnsrelay.txt`。

在项目目录中运行：

```bash
cd pythonProject6
sudo python3 dns_relay.py
```

之所以通常需要 `sudo`，是因为 53 是特权端口；如果 53 已被系统 DNS 服务占用，也会启动失败。为了演示时减少权限或端口冲突，可以改用高位端口：

```bash
python3 dns_relay.py --host 127.0.0.1 --port 10053
```

Python 启动方式同样支持 PPT 格式，例如：

```bash
python3 dns_relay.py -d 8.8.8.8 dnsrelay.txt
```

原有长参数仍然有效，方便指定监听地址、端口和超时：

```bash
python3 dns_relay.py --upstream 8.8.8.8 --config dnsrelay.txt \
  --host 127.0.0.1 --port 10053 --timeout 3
```

随后在另一个终端用 `dig` 查询；高位端口必须加 `-p 10053`。

### 3. 展示本地直接解析（30 秒）

```bash
dig @127.0.0.1 -p 10053 www.bupt.com.cn A
```

要指出的结果：

- 状态是 `NOERROR`。
- Answer 中是 `114.255.40.66`。
- TTL 是 60 秒。
- 程序日志显示 `[LOCAL]`，说明没有访问上游。

本机在 2026-09-10 的实际测试结果：

```text
status: NOERROR
flags: qr aa rd ra
ANSWER: www.bupt.com.cn. 60 IN A 114.255.40.66
```

### 4. 展示域名屏蔽（30 秒）

```bash
dig @127.0.0.1 -p 10053 www.666.com A
```

要指出的结果：

- 状态是 `NXDOMAIN`。
- Answer 数量为 0。
- 程序日志显示 `[NXDOMAIN]`。

本机实际测试结果：

```text
status: NXDOMAIN
flags: qr aa rd ra
ANSWER: 0
```

注意：程序不是把 `0.0.0.0` 当成 A 记录返回，而是把它解释为“该域名不存在”。

还可以验证本地 IPv6 AAAA 记录：

```bash
dig @127.0.0.1 -p 10053 www.bupt.com.cn AAAA
```

Answer 应为 `2001:db8::66`，日志显示 `[LOCAL] ... TYPE=AAAA`。`2001:db8::/32` 是文档示例地址，只用于课程演示，不代表真实公网服务。

### 5. 展示上游转发（40 秒）

```bash
dig @127.0.0.1 -p 10053 www.baidu.com A
```

或者用一个本地表中没有的记录类型，清楚地证明它不会走本地 A 记录：

```bash
dig @127.0.0.1 -p 10053 www.bupt.com.cn AAAA
```

要结合日志解释：

```text
[QUERY] ...
[FORWARD] ... ID=客户端ID->新ID UPSTREAM=114.114.114.114
[RESPONSE] ID 新ID -> 客户端ID 返回 客户端地址
```

这三行体现了接收、ID 改写转发、ID 恢复三个阶段。本机已验证 AAAA 查询能够经上游返回。

### 6. 收尾总结（20 秒）

“所以程序完成了三个核心场景：本地解析、域名屏蔽和透明转发。Transaction ID 映射让不同客户端即使使用相同原始 ID，也能区分各自的响应；锁和超时清理则保证映射表在两个线程之间安全使用并避免长期堆积。”

## 三、一定要真正理解的原理

### 1. 一次查询经过什么流程

```text
客户端
  │ UDP 查询
  ▼
DNS Relay 解析 Header 和 Question
  ├─ 命中黑名单 ──────────────► 构造 NXDOMAIN ─► 客户端
  ├─ 本地 A/IN 命中 IPv4 ─────► 构造 A 响应 ──► 客户端
  ├─ 本地 AAAA/IN 命中 IPv6 ──► 构造 AAAA 响应 ► 客户端
  └─ 未命中
       │ 保存 new_id -> (old_id, 客户端地址, 过期时间)
       │ 把 old_id 改为 new_id
       ▼
     上游 DNS ──► Relay 恢复 old_id ──► 原客户端
```

### 2. DNS 报文结构

DNS Header 固定 12 字节，包括：

- Transaction ID：16 位，用来匹配查询与响应。
- Flags：QR、AA、RD、RA、RCODE 等标志。
- QDCOUNT、ANCOUNT、NSCOUNT、ARCOUNT：问题、回答、权威、附加记录数量。

Question 由 `QNAME + QTYPE + QCLASS` 组成。本程序解析第一个 Question：

- QNAME：例如 `www.baidu.com`，在线路中按 label 编码为 `3www5baidu3com0`。
- QTYPE：1 是 A，28 是 AAAA 等。
- QCLASS：通常 1，即 IN。

### 3. 为什么要改 Transaction ID

Transaction ID 只有 16 位，而且由各客户端独立生成。不同客户端可能同时发来相同 ID。如果直接把原 ID 发给同一个上游 socket，仅凭 ID 无法可靠判断响应属于哪个客户端。因此程序给每个在途查询分配当前未使用的新 ID，并用 `forward_map` 保存新旧 ID 和客户端地址。收到上游响应后，用新 ID 查表并恢复旧 ID。

### 4. 为什么需要锁

主线程会向 `forward_map` 添加映射；上游接收线程会取出映射；清理线程会删除超时映射。三个执行流共享同一个字典，因此用 `threading.Lock` 避免同时修改导致竞争或数据结构异常。

### 5. DNS 压缩指针是什么

DNS 为节省报文空间，可以用两个字节的指针引用报文中之前出现的域名。指针最高两位是 `11`，剩余 14 位是偏移量。本程序的 `parse_domain` 同时处理普通 label 和压缩指针，并用 `visited` 防止恶意指针形成死循环。

### 6. 本程序是不是递归 DNS 服务器

不是。它不会自己从根服务器、顶级域服务器逐级查询；本地不命中时只是把原查询转发给配置的递归上游 `114.114.114.114`。准确称呼是 DNS relay / forwarder。

## 四、老师给一个 IP 时怎么处理

“给一个 IP”有三种可能，先复述确认，不要直接操作错方向。

### 情况 A：老师给的是上游 DNS 服务器 IP

例如老师说用 `8.8.8.8`：

```bash
python3 dns_relay.py --host 127.0.0.1 --port 10053 --upstream 8.8.8.8
dig @127.0.0.1 -p 10053 example.com A
```

观察启动日志中的上游地址和 `[FORWARD]` 日志。当前程序只允许改变上游 IP，上游端口固定为 53。

### 情况 B：老师给的是要写入本地表的目标 IP

需要让老师同时给一个域名，例如 `1.2.3.4 test.example`，在 `dnsrelay.txt` 中新增：

```text
1.2.3.4 test.example
```

然后重启程序（当前版本不支持运行中热加载），再测试：

```bash
dig @127.0.0.1 -p 10053 test.example A
```

只需验证 DNS Answer 是否为老师给出的 IP，不需要该 IP 上真的有网站。

### 情况 C：老师要求输入 IP 反查域名

这是 PTR 反向查询，查询名位于 `in-addr.arpa`。当前程序没有本地 PTR 记录功能，只能把 PTR 请求转发给上游：

```bash
dig @127.0.0.1 -p 10053 -x 8.8.8.8
```

应如实回答：“当前版本会透明转发 PTR 查询；本地配置支持域名到 IPv4 的 A 记录和域名到 IPv6 的 AAAA 记录，但没有本地 PTR 反向映射。”

## 五、老师高概率提问与参考回答

### Q1：为什么 DNS 使用 UDP？

普通 DNS 查询通常报文小，UDP 无需建立连接，开销和时延低。DNS 也会使用 TCP，例如响应被截断、报文较大或区域传送。我们的当前版本只实现 UDP，这是功能边界之一。

### Q2：为什么不直接使用客户端原来的 ID？

多个客户端可能使用相同的 16 位 ID。中继器共享一个上游 socket，改成当前唯一的新 ID 后，才能通过映射表准确找到原客户端，并在返回前恢复原 ID。

### Q3：ID 为什么是 16 位？会不会冲突？

DNS Header 的 Transaction ID 固定为 16 位，范围是 0～65535。程序随机尝试生成未占用 ID，失败后顺序扫描整个空间；只要在途请求没占满 65536 个，就不会复用映射表中已有的 ID。

### Q4：本地支持哪些记录类型？

A 表示 IPv4，AAAA 表示 IPv6，当前本地表支持这两种 IN 记录。同一域名可以同时配置 IPv4 和 IPv6。MX、PTR 等类型没有本地数据结构，因此转发给上游。

### Q5：`0.0.0.0` 为什么返回 NXDOMAIN？

这是程序约定的屏蔽标记。命中后返回 RCODE=3 和零条 Answer，使客户端认为域名不存在。另一种设计也可以返回 A=0.0.0.0，但当前实现选择 NXDOMAIN。

### Q6：TTL 是多少？作用是什么？

本地 A 响应的 TTL 固定为 60 秒，表示缓存解析器最多可缓存该记录 60 秒。转发响应的 TTL 不修改，保持上游原值。

### Q7：如何处理大小写和末尾的点？

加载配置和解析查询时都转为小写并去掉末尾点，所以 `WWW.BUPT.COM.CN.` 能匹配 `www.bupt.com.cn`。

### Q8：为什么有三个线程/执行流？

主线程接收客户端请求；后台接收线程等待上游响应；后台清理线程每秒删除过期映射。这样等待上游时不会阻塞新的客户端查询。

### Q9：上游超时后客户端收到什么？

当前实现只会在超时后删除映射并打印 `[TIMEOUT]`，不会主动给客户端返回 SERVFAIL，所以客户端最终由自己的超时机制结束等待。这是已知缺陷，改进方式是清理时保存足够信息并发送 SERVFAIL。

### Q10：如何防止 DNS 压缩指针死循环？

解析过程中记录访问过的偏移量；如果再次访问同一偏移，就判定报文非法并停止解析。同时检查指针和 label 是否越界、label 是否超过 63 字节。

### Q11：什么是 QR、AA、RD、RA、RCODE？

- QR：0 为查询，1 为响应。
- AA：响应者是否声称自己对该结果具有权威性。
- RD：客户端是否请求递归，本程序在响应中保留请求的 RD。
- RA：服务端是否提供递归能力。
- RCODE：0 是成功，1 是格式错误，2 是服务失败，3 是域名不存在。

### Q12：配置文件修改后会自动生效吗？

不会。配置只在启动时加载，修改后要重启程序。

### Q13：能同时服务多个客户端吗？

可以处理多个 UDP 在途查询，映射表按新 Transaction ID 区分请求。但它仍是教学实现，没有线程池、限流、容量控制和生产级压力测试。

### Q14：程序如何处理非法报文？

它检查最小 12 字节 Header、QR 必须是 Query、域名格式、指针循环与越界、QTYPE/QCLASS 字节是否存在。失败时尽量返回 FORMERR。它还没有完整校验所有 DNS Header 计数和全部 Section。

### Q15：为什么 Answer 里的名字是 `C0 0C`？

这是压缩指针，指向报文偏移 12，也就是 Question 中 QNAME 的起点，避免在 Answer 中重复写一遍完整域名。

## 六、当前实现的缺陷（答辩时主动承认但要说明改法）

### 关键缺陷

1. **只支持 UDP，不支持 TCP。** 大响应如果带 TC 截断标志，程序不会通过 TCP 重试；客户端若改用 TCP 连接本中继器也无法使用。
2. **上游超时不给客户端 SERVFAIL。** 清理线程只删映射，客户端会无响应地等到自身超时。
3. **不验证上游响应来源。** `recvfrom` 得到的源地址被忽略，只要有人能向上游 socket 投递猜中新 ID 的报文，就可能被接受；还应校验来源 IP/端口、QR、Question 等。
4. **对外监听可能成为开放解析器。** 默认监听 `0.0.0.0:53`，若暴露到公网，可能被滥用做 DNS 放大攻击；应限制监听地址、来源 ACL、速率和最大在途请求数。
5. **没有缓存。** 所有本地未命中的重复查询都会访问上游，效率不如完整转发器。

### 协议完整性缺陷

6. 本地支持 A/IN 和 AAAA/IN，但没有本地 CNAME、MX、PTR 等记录。
7. 只解析第一个 Question，没有严格验证 `QDCOUNT == 1`，也没有完整校验 Answer/Authority/Additional Section。
8. 本地 NXDOMAIN 没带 SOA 权威记录，不利于规范的负缓存。
9. 本地响应设置了 AA，严格来说这个教学配置表并不是一个完整的权威 DNS 区；AA 的语义不够严谨。
10. 本地构造的响应不回显 EDNS OPT，也没有显式处理 EDNS、DNSSEC 和超过缓冲区的报文。
11. 只使用 IPv4 socket，不能让 IPv6 客户端连接或配置 IPv6 上游。

### 工程性缺陷

12. 配置不支持热加载、通配符和重复项告警；重复域名会由最后一条静默覆盖。
13. `MAP_TIMEOUT` 常量没有实际使用，真正使用的是命令行 `--timeout`。
14. 上游端口写死为 53，`--upstream` 只能填 IP，不能方便地指定 `IP:端口` 或多个备用上游。
15. 绑定错误提示只强调 Windows；实际上 macOS/Linux 绑定 53 端口通常也需要 root 权限。
16. 日志仍以标准输出为主，虽然已经支持 `-d` / `-dd` 调试级别，但还没有日志轮转、结构化文件记录或统计指标。

推荐回答结构：**先承认边界 → 说明当前设计为什么足以完成课程核心目标 → 给出明确改进方案。** 例如：“是的，当前只实现 UDP，这是教学版本的边界；核心的本地解析、屏蔽、转发和 ID 映射已经实现。如果扩展，我会增加 TCP 监听，并在上游 UDP 响应 TC=1 时用 TCP 重试。”

## 七、验收前操作清单

- 确认在 `pythonProject6` 目录启动，否则默认找不到 `dnsrelay.txt`。
- 检查 Python：`python3 --version`。
- 检查语法：`python3 -m py_compile dns_relay.py`。
- 检查 53 端口是否占用：macOS/Linux 可用 `sudo lsof -nP -iUDP:53`。
- 提前决定使用 53 端口还是演示用 10053 端口。
- 准备两个终端：左侧运行程序看日志，右侧运行 `dig`。
- 依次测试本地命中、NXDOMAIN、上游转发。
- 若改了 `dnsrelay.txt`，务必重启程序。
- 若上游不通，换一个现场网络允许访问的 DNS，例如老师指定的 DNS；不要把网络故障误说成代码错误。

## 八、现场故障应对

### 启动时报 Permission denied

53 端口需要管理员权限。使用 `sudo`，或改为 `--port 10053`。

### 启动时报 Address already in use

53 端口已占用。查占用进程，或改用 10053，不要现场贸然终止不认识的系统进程。

### 本地记录不生效

检查启动日志是否显示“加载完成，共 3 条记录”；确认工作目录和 `--config` 路径；确认查询类型与配置地址族一致；修改配置后重启。

### 本地命中正常，但外部域名超时

说明 Relay 的监听和本地响应路径正常，问题集中在上游连通性。检查 `[FORWARD]` 后是否出现 `[RESPONSE]`；尝试老师指定的上游 DNS或现场网络可访问的 DNS。

### `dig` 不存在

Windows 可使用：

```powershell
nslookup www.bupt.com.cn 127.0.0.1
```

但 `nslookup` 不便指定 10053 端口，因此 Windows 上最好直接用管理员权限运行 53 端口，或预先准备支持指定端口的查询工具。

## 九、最后一段可直接背诵的总结

“这个项目的核心不是调用现成 DNS 库，而是直接处理 DNS 二进制报文。我们完成了 Question 中域名、类型和类别的解析，能构造本地 A 与 NXDOMAIN 响应；对于未知查询，通过新的 Transaction ID 建立请求与客户端之间的映射，再透明转发上游响应。这样既实现了本地域名表和屏蔽，也处理了多客户端 ID 冲突。当前版本定位为教学型 UDP DNS Relay，主要不足是没有 TCP、缓存、超时错误回包和完整的安全校验，这些是后续生产化时最先要补的部分。”
