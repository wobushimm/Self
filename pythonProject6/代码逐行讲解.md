# `dns_relay.py` 代码逐行讲解与答辩口述

这份讲解对应当前 1126 行的源文件。源文件为了排版加入了很多空行，因此这里按“连续语句块”解释，但每一条有效语句都覆盖到。

## 0. 先建立整幅图

程序有三个执行流：

1. 主线程：接收客户端请求，决定本地回答还是转发。
2. 上游接收线程：接收上游 DNS 响应，根据新 ID 找回原客户端。
3. 超时清理线程：定期删除长期没有响应的映射。

程序有两个 UDP socket：

- `listen_sock` 面向客户端，默认绑定 `0.0.0.0:53`。
- `upstream_sock` 面向上游 DNS，绑定系统随机分配的本地端口。

程序有两个主要字典：

- `domain_table`：本地域名到 IP 的映射。
- `forward_map`：中继时的新 ID 到原 ID、客户端地址和过期时间的映射。

## 6. 第 140～244 行：解析域名 `parse_domain`

这是最容易被老师指着问的函数。

### 第 140～168 行：输入、返回值与状态

```python
def parse_domain(data: bytes, start: int = 12) \
        -> Tuple[Optional[str], int]:
```

- `data` 是完整 DNS 报文的原始字节。
- `start=12` 因为 DNS Header 固定为 12 字节，Question 的 QNAME 通常从偏移 12 开始。
- 成功返回 `(域名, 原始 QNAME 结束位置)`；失败返回 `(None, start)`。
- `labels` 保存 `www`、`baidu`、`com` 等分段。
- `pos` 是当前读取位置。
- `visited` 保存访问过的偏移，防止压缩指针循环。
- `jumped` 表示是否通过压缩指针跳转过。
- `end_pos` 保存原始字段的结束位置，不能简单使用跳转后的 `pos`。

### 第 170～188 行：循环和结束标志

每轮先检查 `pos` 是否越过报文，以及是否重复访问。`length = data[pos]` 读取 label 的长度字节。

普通域名的线路编码示例：

```text
03 www 05 baidu 03 com 00
```

遇到 `length == 0` 表示域名结束。如果从未跳转，原字段结束位置是 `pos + 1`，然后 `break`。

### 第 190～210 行：压缩指针

```python
if (length & 0xC0) == 0xC0:
```

`0xC0` 的二进制是 `11000000`。DNS 压缩指针前两位必须是 `11`，按位与用来检测它。

```python
offset = ((length & 0x3F) << 8) | data[pos + 1]
```

这句把指针的低 14 位拼成偏移：第一字节去掉高两位后左移 8 位，再和第二字节做按位或。

第一次遇到指针时，原始 QNAME 在这两个指针字节之后结束，所以记录 `end_pos = pos + 2`。随后把 `pos` 改成指针目标继续解析实际域名，并设 `jumped=True`。

### 第 212～241 行：普通 label

- 单个 label 最长 63 字节，超出视为错误。
- `pos += 1` 越过长度字节。
- `pos + length > len(data)` 防止切片越界或截断报文。
- `data[pos:pos + length]` 取出 label。
- DNS 的基础主机名在线路中使用 ASCII；解码失败就返回错误。
- `labels.append` 保存分段，`pos += length` 移动到下一段。
- 循环结束后，用点连接、转小写、去末尾点。

第 243～244 行是最后一道保护：任何未预料异常都转成解析失败。答辩时不要只说“防报错”，应说“网络输入不可信，错误报文不能使服务进程退出”。

## 7. 第 251～294 行：解析 Question

先验证报文至少有 12 字节，然后从偏移 12 解析 QNAME。QNAME 后紧跟两个 16 位字段：QTYPE 和 QCLASS，共 4 字节。

```python
qtype = int.from_bytes(data[pos:pos + 2], "big")
qclass = int.from_bytes(data[pos + 2:pos + 4], "big")
```

网络协议使用大端字节序，`big` 表示高位字节在前。例如 `00 01` 转成整数 1，即 A 或 IN。

`question_end = pos + 4` 供构造响应时精确复制原 Question。返回四元组：域名、查询类型、查询类别、Question 结束位置。

当前缺陷：没有读取并验证 Header 中的 `QDCOUNT`，只解析第一个 Question。

## 8. 第 301～359 行：构造错误响应

### 第 313～325 行

连 ID 的两个字节都没有就无法构造可匹配的响应，因此返回空字节。否则复制原 Transaction ID。若有 Flags，就解析请求 flags；目的是保留客户端的 RD 位。

### 第 327～336 行：拼 Flags

```python
flags = 0x8000 | (request_flags & 0x0100) | 0x0080 | rcode
```

- `0x8000`：设置 QR=1，表示响应。
- `request_flags & 0x0100`：只取原请求 RD 位。
- `0x0080`：设置 RA=1。
- `rcode`：写入低 4 位，1 是 FORMERR，2 是 SERVFAIL。
- `|` 是按位或，把不同标志合并进一个 16 位数。

### 第 338～359 行：Header 和 Question

如果报文至少有 Header，就暂定 `QDCOUNT=1`，否则为 0；三个响应 Section 的计数全为 0。用 `flags.to_bytes(2, "big")` 把整数转回网络字节序，再用 `+` 拼接 byte 串。

缺陷：只凭长度至少 12 就把 `request[12:]` 全当作 Question，且宣称 Question 数为 1。恶意或复杂报文可能使计数与实际内容不一致。

## 9. 第 366～460 行：构造本地 A 响应

### 第 374～400 行：前置检查

重新解析 Question，确保它有效。只允许 QTYPE=1（A）和 QCLASS=1（IN）。`socket.inet_aton(answer_ip)` 把例如 `114.255.40.66` 变成四字节 RDATA。

### 第 402～427 行：响应 Header

复制原 ID并读取请求 Flags。生成的 Flags 设置：

- QR=1：这是响应。
- AA=1：当前代码声称本地答案是权威答案。
- RD：保持客户端原值。
- RA=1：声称支持递归。

计数为 `QDCOUNT=1`、`ANCOUNT=1`、其他为 0。

需要诚实说明：教学配置表并非完整权威区，严格来说设置 AA 值得商榷。

### 第 429～454 行：Question 与 Answer

```python
question = request[12:question_end]
name_pointer = b"\xC0\x0C"
```

复制原 Question。`C0 0C` 是压缩指针，指向偏移 `0x000C=12` 的 QNAME，避免在 Answer 重复写域名。

Answer 按 RFC 1035 的资源记录格式拼接：

```text
NAME | TYPE | CLASS | TTL | RDLENGTH | RDATA
C00C | 0001 | 0001  | 0000003C | 0004 | 四字节IP
```

- `0001`：A 和 IN。
- `0000003C`：十六进制 3C 等于十进制 60，TTL 60 秒。
- `0004`：RDATA 长度为 4。

最后返回 `header + question + answer`。

## 10. 第 467～518 行：构造 NXDOMAIN

这个函数与 A 响应相似，但：

- Flags 低四位加入 `0x0003`，RCODE=3，即 Name Error/NXDOMAIN。
- `ANCOUNT=0`，不构造 Answer。
- 只返回 `header + question`。

`_, _, _, question_end = parsed` 中的 `_` 表示这些返回值不需要使用。

缺陷：规范的权威 NXDOMAIN 通常应在 Authority Section 带 SOA，便于负缓存；当前教学实现没有。

## 11. 第 525～549 行：生成新 DNS ID

```python
for _ in range(100):
    new_id = random.randint(0, 65535)
```

DNS ID 是 16 位，因此范围 0～65535。每次在锁内检查 `new_id not in forward_map`。随机尝试最多 100 次，通常能快速找到空 ID。

如果连续冲突，就在锁内顺序扫描全部 65536 个值。若全部被占用，抛出 `RuntimeError("DNS ID 已耗尽")`。

为什么既随机又扫描：随机让 ID 不容易预测且平均速度快；顺序扫描保证只要仍有空位就能找到。

## 12. 第 556～583 行：超时清理线程

`while True` 使线程永久运行。每轮获取当前时间，在锁内遍历映射，把已经过期的 ID 收集到 `expired`，随后删除。

为什么先收集再删除：不能在直接遍历字典时改变字典大小，否则 Python 会报错。

释放锁后再打印日志，最后 `time.sleep(1)`，所以清理精度约为 1 秒。

重要缺陷：这里只删除映射，没有向客户端发送 SERVFAIL。因此上游超时时，客户端会一直等到自身超时。

## 13. 第 590～670 行：接收上游响应

### 第 595～619 行

线程永久阻塞在 `upstream_sock.recvfrom(BUF_SIZE)` 等待响应。返回值包括响应字节和来源地址，但代码用 `_` 丢弃来源地址。

先验证响应至少 12 字节，然后从前两个字节解析新 ID。在锁内执行：

```python
mapping = forward_map.pop(new_id, None)
```

`pop` 同时查找并删除，防止同一响应被重复处理；不存在时返回 `None`。

### 第 621～658 行

没有映射可能表示请求已超时、重复响应或非预期报文，因此丢弃。找到后解包原 ID、客户端 IP和端口。

```python
response = old_id.to_bytes(2, "big") + response[2:]
```

只替换响应前两个字节，保留上游返回的其余 DNS 内容。随后通过 `listen_sock.sendto` 发给原客户端。

### 第 660～670 行

捕获 socket 错误和其他异常，保证后台线程尽量不退出。

安全缺陷：代码没有校验 `recvfrom` 返回的来源地址，也没有校验响应的 QR、域名和查询类型。随机新 ID只能降低伪造概率，不能替代完整校验。

## 16. 第 846～965 行：接收和检查客户端请求

### 第 846～881 行

主循环通过 `listen_sock.recvfrom` 阻塞等待 UDP 数据报。它同时得到请求 bytes 和 `(客户端IP, 客户端端口)`。

DNS Header 少于 12 字节就记录 FORMERR，并尽可能构造错误响应。`continue` 表示结束当前循环，继续等下一条请求。

### 第 887～913 行：取 QR 位

```python
flags = int.from_bytes(request[2:4], "big")
qr = (flags >> 15) & 1
```

Flags 位于 Header 的第 2～3 字节。QR 是最高位，所以右移 15 位，再和 1 做按位与。Relay 面向客户端只接收查询，因此 QR 必须为 0；若收到响应报文则返回 FORMERR。

### 第 919～965 行：解析和记录查询

调用 `parse_question`。失败则返回 FORMERR。成功后解包域名、类型和类别。字典把常见 QTYPE 数字转为便于阅读的名字；`.get(qtype, str(qtype))` 表示未知类型就显示其数字。最后打印 `[QUERY]` 日志。

## 17. 第 971～1008 行：本地处理分支

只有同时满足以下条件才查本地表：

```python
qtype == 1 and qclass == 1 and domain in domain_table
```

也就是 A、IN、本地域名存在。命中后：

- IP 是 `0.0.0.0`：调用 `build_nxdomain_response`。
- 其他 IP：调用 `build_local_a_response`。

通过监听 socket 把响应发回客户端，随后 `continue`，所以本地命中不会执行上游转发代码。

注意源代码第 1010 行附近的注释“非 A / 非 IN 请求直接转发”不够完整；实际是所有**未在本地 A/IN 表命中**的请求都会转发，包括普通 A 查询未命中。

## 18. 第 1019～1054 行：建立转发映射和改 ID

先从请求前两字节取出客户端原 ID，调用 `generate_dns_id` 获取当前映射表中未占用的新 ID，再计算过期时间：

```python
expire_time = time.time() + args.timeout
```

在锁内保存：

```python
forward_map[new_dns_id] = (
    old_dns_id, client_ip, client_port, expire_time
)
```

然后构造上游数据包：

```python
forward_packet = new_dns_id.to_bytes(2, "big") + request[2:]
```

它只改 Transaction ID，其余报文完全透明转发。

老师问“为什么要改 ID”时回答：多个客户端独立生成 ID，可能相同；中继器用同一个上游 socket，必须给每个在途请求一个中继器范围内唯一的新 ID，才能把响应送回正确客户端。

## 19. 第 1060～1099 行：发送上游

`upstream_sock.sendto(forward_packet, upstream_dns)` 把请求发给上游。UDP 的 `sendto` 成功只表示数据交给本机网络栈，不表示上游已经收到或会回答。

若发送本身抛异常，程序会：

1. 在锁内删除刚保存的映射。
2. 构造 RCODE=2 的 SERVFAIL。
3. 返回客户端并记录日志。
