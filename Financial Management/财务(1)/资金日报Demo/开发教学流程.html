从业务动作到可维护工具

财务小工具开发
教学流程

先把人工工作说清楚，再把确定的规则交给程序执行；让业务规则沉淀下来，而不是只依赖某个人的经验。

开发原则八步流程字段与规则分期建设分工与测试
01 / 先理解问题

代码不是起点，业务流程才是

开发财务工具前，先把每天的人工动作、输入文件、输出结果、判断规则和异常情况拆开。规则清楚的自动做，不确定的保留人工审核。

“我们不是让程序替财务判断，而是让程序稳定完成重复、确定、可追溯的动作。”
梳理业务→固定输入输出→设计规则→制作 Demo→测试迭代
02 / 八步开发法

从人工操作到可运行工具

第一步：写下现有人工流程

先回答：数据从哪里来？最后要交付什么？每天重复做什么？哪些地方必须人工判断？以资金日报为例，就是司库导出、收付分类、余额汇总和日报核对。

第二步：拆分输入、规则与结果

原始数据不修改，业务规则单独维护，结果文件单独输出。这样既便于追溯，也能避免每天重新配置。

第三步：建立字段映射

逐列确认“从哪里来、写到哪里去、是否需要公式”。字段映射解决数据搬运问题，不负责业务分类。

第四步：按确定性设计规则

把高确定性规则放前面；模糊、冲突或没有规则的情况进入待审核清单，绝不为了自动化率而猜测。

第五步：先做最小 Demo

第一版只验证“能否正确读取、分类并输出收付明细”。不急于先做大网站、复杂权限或透视表自动刷新。

第六步：用异常案例测试

正常数据只能证明工具能跑；冲突摘要、重复数据、金额异常、规则缺失等才能验证工具不会误处理。

第七步：接入正式总表

将确认后的结果去重并追加到历史明细库，再由公式和汇总表生成日报。历史数据只能追加，不应被重写。

第八步：最后再接入前端与 Git

当核心规则稳定后，再将 Python 能力封装成接口，由公司页面负责上传、展示状态和下载结果。

03 / 结构化设计

先让每一列都有清楚来源

INPUT

当天司库文件

仅保存当天原始交易。程序读取，不覆盖，不靠人工修改原始记录。

RULE

规则配置文件

保存字段映射、特殊摘要规则和模板；它是可维护的“业务说明书”。

OUTPUT

资金日报总表

保存历史收付明细，并通过公式或透视表形成日报和余额监控。

收付明细字段数据来源处理方式
日期、年-月司库交易日期直接写入并格式化
银行账号、往来单位司库银行账号、对方户名直接映射
收入、支出司库收款金额、付款金额直接映射
编码、收付项目摘要与规则库自动分类或转人工审核
余额上笔余额、收入、支出公式计算
04 / 规则设计

先确定，再兜底

收款
收款金额有值
直接归为 1、销售收款。
付款标注
摘要只含“采购 / 费用 / 内部往来”之一
直接归类为采购付款、费用支出或内部往来。
固定业务
没有人工标注
查询“特殊摘要规则”，例如 包含｜网银服务年费｜3｜3、费用支出。
人工审核
多个标注、规则冲突或没有规则
进入 H_I待配置，由财务确认后再沉淀为规则。
为什么不让程序自动猜？
资金分类会影响日报口径。错误自动化比少量人工审核风险更高，因此采用“高确定性自动、低确定性待审核”的保守设计。每一次确认都可以成为下一次的规则，让工具逐步成长。
05 / 分期建设

先跑通，再自动化

第一期：收付明细 Demo

上传司库文件，自动完成字段填充与 H/I 分类，输出 H_I待配置。先验证规则、格式和异常处理。

第二期：接入资金日报总表

自动去重、追加历史收付明细；将上一日 B18 写入 B2，更新 A1 日期，输出新的总工作簿。

第三期：前端与汇总自动化

接入公司 UI，完成上传、进度展示和下载。透视表刷新根据实际 Windows/WPS/Excel 环境再确定方案。

一句话总结

开发财务小工具，不是先学会多少代码，而是先把人工业务讲清楚：输入是什么、结果是什么、规则是否确定、异常由谁判断。业务梳理清楚后，代码只是把规则稳定地执行出来。
